# Sentinel-1 wetness indicator: implementation summary

This note summarizes the implementation, output evidence, assumptions, and
limitations for the Sentinel-1 wetness indicator.

## Requirement-to-implementation map

| Requirement | Implementation and evidence |
|---|---|
| Documented source, stable identifiers, reproducible input | Intended source: [Copernicus Sentinel-1](https://dataspace.copernicus.eu/data-collections/copernicus-sentinel-missions/sentinel-1). The processor accepts local, dual-band GeoTIFFs with scene/product IDs, acquisition timestamps, relative orbit, band indices, and declared sigma0 units. Output feature IDs are deterministic: `s1wet:<tile>:<date>:<row>:<column>`. Four deterministic synthetic scenes are generated by [`scripts/create_sentinel1_demo.py`](./scripts/create_sentinel1_demo.py). Synthetic data are used instead of live imagery because time and resource constraints prevented obtaining and preparing a real scene; the fixtures are not Copernicus products. |
| VV/VH math and temporal baseline | [`app/satellite/soil_moisture.py`](./app/satellite/soil_moisture.py) accepts linear power or dB; dB is converted using `10 ** (dB / 10)`. It takes per-pixel medians of earlier valid observations in linear power, then computes `10 * log10(current / baseline_median)` independently for VV and VH. By default, at least three earlier observations are required per polarization and pixel. A wetness candidate is flagged only when both anomalies are at least the configured threshold (default 1 dB). |
| Typed interface, assumptions, boundary and failure tests | `RasterGrid` and `Acquisition` define typed inputs; `analyze` returns a GeoJSON FeatureCollection and quality-report dictionary. Validation rejects invalid CRS, dimensions, timestamps, orbit, configuration, and inadequate baseline. [`tests/test_sentinel1_soil_moisture.py`](./tests/test_sentinel1_soil_moisture.py) checks dB/linear equivalence, dual-polarization behavior, nodata and invalid samples, median response to an isolated outlier, CRS, alignment, orbit, and baseline failures. |
| Metric spatial processing and geometry validation | Inputs must share a precisely aligned EPSG:25832 grid. Pixel polygons are constructed and checked in that projected CRS, then reprojected to longitude/latitude for GeoJSON output. |
| Representative result and quality/error report | [`examples/sentinel1_demo_result.geojson`](./examples/sentinel1_demo_result.geojson) and its companion [`examples/sentinel1_demo_result_quality_report.json`](./examples/sentinel1_demo_result_quality_report.json) are generated from the synthetic fixture. The report records inputs and SHA-256 hashes, baseline scenes and dates, coverage, rejected-pixel reasons, and candidate count. The validated example has 4 total pixels, 3 valid (75% coverage), 1 rejected for current VH nodata, and 1 dual-polarization candidate. The candidate's VV and VH anomalies are each approximately +2 dB. |
| Pinned dependencies, example configuration, Docker | Task-specific exact dependency pins are in [`requirements-sentinel1.txt`](./requirements-sentinel1.txt); configuration is in [`examples/sentinel1_soil_moisture.config.example.json`](./examples/sentinel1_soil_moisture.config.example.json). [`Dockerfile`](./Dockerfile), [`.dockerignore`](./.dockerignore), and the opt-in `satellite` service in [`docker-compose.yml`](./docker-compose.yml) package and run the fixture workflow. The Compose run completed successfully and wrote its result under `data/sentinel1_demo/`. |
| Provenance, run instructions, schema, limitations | The project [`README.md`](./README.md#sentinel-1-soil-wetness-candidate-indicator) documents the source, execution, output properties, assumptions, and known gaps. |

## Method and output

The current scene is the latest timestamp in the configured acquisitions;
earlier scenes alone form the baseline. All scenes must be on the same aligned
EPSG:25832 grid and share one Sentinel-1 relative orbit. GeoTIFF masks and
nodata values are excluded, as are non-finite or non-positive linear powers.
An output feature is emitted only where both current polarizations and the
minimum required baseline samples are valid.

Each feature contains the scene/product IDs, acquisition time, relative orbit,
source row and column, VV and VH anomalies in dB, baseline counts, threshold,
and boolean `wetness_candidate`. The quality report distinguishes missing
current samples from insufficient baseline coverage. The GeoJSON file is a
proposed `iris_staging` handoff, not a database write.

## Example quality report

The emitted synthetic report has status `ok`, uses 2025-03-09 UTC as the
current acquisition, and compares it with three same-orbit baseline scenes
from 2025-02-01 through 2025-02-25 UTC. The illustrative 2-by-2, 20 m grid
contains 4 pixels: 3 valid (75% coverage) and 1 rejected because current VH is
nodata (`-9999`). There are no rejected current VV samples or insufficient
baseline pixels. One valid pixel meets the 1 dB threshold in both polarizations
(approximately +2 dB VV and +2 dB VH); a VV-only increase is not flagged. The
same report is generated by Docker and records scene identifiers, raster
hashes, input bands, and rejected-pixel reason counts.

The result describes only the synthetic fixture, not real Sentinel-1 geographic
coverage or measured soil wetness. Nodata is honored and the temporal median
reduces sensitivity to an isolated outlier, but there is no spatial speckle
filter or ancillary masking. Vegetation, roughness, water, topography,
seasonality, crop state, and acquisition geometry may also change backscatter;
the candidate flag is not a causal claim.

## Provenance and uncertainty

- **Imagery available for this submission:** synthetic only. Synthetic data are
  used instead of live imagery because time and resource constraints prevented
  obtaining and preparing a real Sentinel-1 scene. No live product was selected
  or downloaded; therefore there is no real acquisition provenance, geographic
  coverage, or imagery-license attribution to claim.
- **Fixture dates and resolution:** synthetic timestamps are 2025-02-01,
  2025-02-13, 2025-02-25, and 2025-03-09 UTC; the 20 m grid is illustrative,
  not a measured resolution of a Sentinel-1 product.
- **Licensing:** actual Sentinel data are available under the
  [Copernicus Sentinel Data Legal Notice](https://sentinels.copernicus.eu/documents/247904/690755/Sentinel_Data_Legal_Notice).
  Preserve product attribution and confirm the applicable notice when real
  products are chosen. The synthetic fixture does not represent a licensed
  Sentinel product.
- **Masks:** the fixture contains one current VH nodata pixel (`-9999`), which
  is rejected and counted. No Sentinel-derived water, layover, shadow,
  incidence-angle, or land-cover masks are provided or applied.
- **Speckle and interpretation:** a three-or-more-scene temporal median makes
  the baseline less sensitive to one isolated outlier; no spatial speckle
  filter is used. Backscatter change is only a wetness *candidate* indicator,
  not a direct soil-moisture measurement and not evidence of causation.
- **Known uncertainty:** vegetation, roughness, water, topography, freeze/thaw,
  crop state, seasonality, acquisition geometry, and processing differences
  can alter backscatter. The workflow does not calibrate raw DN, retrieve
  volumetric soil moisture, apply terrain correction or ancillary masks, or
  validate against ground measurements. The user must supply consistently
  calibrated, terrain-corrected sigma0 products and choose a representative
  same-orbit baseline.
- **Scale:** processing holds arrays in memory and emits one feature per valid
  pixel. Large scenes require windowed processing and a raster-native or
  batched output contract before production use.

## Reproduction and validation

From the repository root:

```bash
python -m pip install -r requirements-sentinel1.txt
python scripts/create_sentinel1_demo.py
python -m app.satellite.soil_moisture \
  --config examples/sentinel1_soil_moisture.config.example.json \
  --output examples/sentinel1_demo_result.geojson
python -m unittest discover -s tests -v
docker compose --profile satellite run --build --rm sentinel1-soil-moisture
```

Validation completed: all 8 automated tests pass; the Docker image builds and
the Compose service produces the stated 3/4 coverage, nodata rejection, and
candidate result. The demo output is synthetic and is evidence that the
pipeline runs, not evidence of scientific accuracy on real imagery.
